# Contributing to Astro Cortex

This project uses a hybrid workflow: most code is generated by ZCode (GLM 5.3)
and reviewed/committed by a human maintainer. This document describes the
conventions that keep the codebase coherent across many AI-assisted iterations.

## LLM-assisted development rules

### 1. Determinism first

Before asking an LLM to implement a feature, ask: *can this be solved with
fixed rules or arithmetic?* If yes, the LLM's job is to write that logic once,
cleanly, with tests. The result is a deterministic module that never needs an
LLM call at runtime.

Examples of deterministic-by-design modules:
- `app/engine/rating.py` — pure function, threshold comparisons
- `app/engine/normalizer.py` — unit conversions, field mappings
- `app/engine/verifier.py` — forecast vs actual comparison (SQL + arithmetic)
- `app/sources/<name>.py` — HTTP fetch + JSON extraction (no judgment)
- `app/db/operations.py` — CRUD layer

Examples where LLM judgment is appropriate (and only at development time):
- Choosing between architectural approaches
- Generating natural-language Telegram message templates
- Debugging unexpected values (root cause analysis)
- Writing docstrings and comments

### 2. Pure functions for the core

The rating engine is a pure function. Keep it that way. If you find yourself
adding I/O or state to `rating.py`, stop — that logic belongs in `crawl/heavy.py`
or `alerting/logic.py`.

### 3. Thresholds are constants, not magic numbers

Every threshold (`DSO_CLOUD_MAX`, `WIND_WARNING_KMH`, etc.) lives in
`app/config.py` as a named, env-overridable constant. Never hardcode a
number in a `.py` file. If you need a new threshold, add it to `Settings`
and reference it via `settings.<name>`.

### 4. Source modules are isolated

Each source module knows nothing about other sources. If you need cross-source
logic (fallback priority, weight blending), that lives in `cascade.py`.
Sources expose `fetch()` and optionally `fetch_forecast()`; everything else
is implementation detail.

### 5. Tests are mandatory for rating logic

Any change to `app/engine/rating.py` MUST come with a corresponding test in
`tests/test_rating.py`. The test should assert specific input/output pairs
that document the intended behavior. If a threshold changes, update both
the constant and the test.

Source modules and DB operations are not currently unit-tested (they require
fixtures for HTTP and SQLite). Integration tests may be added later.

### 6. Secrets never get committed

- `.env` is in `.gitignore` — verify with `git status` before every commit
- API keys live in `.env`, referenced via `os.environ.get()` in code
- SSH keys live in `~/.ssh/`, never in the repo
- Telegram tokens are passed via env var

If you suspect a secret was committed:
```bash
git log -p --all | grep -E "(token|key|secret|password)" | head -20
```
If found, follow the remediation steps in `docs/ARCHITECTURE.md`.

## Commit conventions

- Use conventional commit prefixes: `feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:`
- Reference issue numbers in commit body if applicable
- Keep commits atomic — one logical change per commit
- Push to `main` only after local tests pass (`pytest tests/`)

## Pull request workflow

1. Create a feature branch: `git checkout -b feat/<short-description>`
2. Implement + test locally
3. Push: `git push -u origin feat/<short-description>`
4. Open PR on GitHub
5. Merge after review (or self-merge for solo project if confident)

## Architecture questions

Before changing the architecture, document the question in `docs/ARCHITECTURE.md`
and discuss. The current design has explicit reasons — read them before
replacing them.
